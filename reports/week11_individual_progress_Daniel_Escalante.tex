\section{Setbacks and how I addressed them}
\begin{itemize}
  \item \textbf{Validation would have crashed.} The best-metric setting expects \texttt{eval\_loss}, which per-patient validation does not report. I cancelled jobs 49874617--49874620 first. Commit \texttt{4d22c70} drops that setting and validates once per epoch. One pass takes about 80 minutes, so the old schedule would have added about 50 GPU-hours per arm. Smoke job 49889947 passed, and every finished arm passed both epoch checks.
  \item \textbf{Out of memory at step 333} (\texttt{decision\_only}, job 49889996): 12.31\,GiB needed, 12.27\,GiB free, 4.70\,GiB fragmented. I resumed with expandable allocator segments (job 49924900) and then set that allocator in every stage (\texttt{7fcd9e5}).
  \item \textbf{Crash at step 1,340} in the three hypothesis arms (jobs 49889995, 49889997, 49889998). Upstream runs \texttt{str.format} on the whole episode, and that record contains braces. A failing test led to a literal substitution in \texttt{7fcd9e5}. Smoke job 50010187 passed, and the finished run passed that step.
  \item \textbf{Class memory cap.} Other jobs held about 240--246 of 250\,GB, so S4 waited. Host memory peaked at 6.8\,GB; queued requests dropped from 40\,GB to 16\,GB. CPU-only S4--S6 moved to the burst QOS. GPU evaluation waited 6~h 40~min to 7~h 20~min, then finished in 24--33 minutes each.
\end{itemize}
